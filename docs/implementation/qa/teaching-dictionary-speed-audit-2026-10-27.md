## Source findings and likely cost

1. **Default list requests more data than the 50 visible words need.** `app/(authenticated)/admin/teaching-dictionary/page.tsx` starts `loadCachedTeachingDictionaryEvidenceAuthority()` for every filter (line 87). Its cold path goes through `lib/teaching-dictionary-manager/evidence-authority.ts` into the unscoped relationship repository, which pages through canonical words, spelling mappings/events, support, members, pair decisions, and other authorities (`lib/adle/word-skill-relationships/repository.ts`, around lines 212–227). The cache has a 60-second TTL and mutation tag; a warm cache reduces Supabase work, but every cold read reconstructs global authority. The list then performs a paginated word RPC, recent-draft read, metadata and dictation reads, and six route-fact reads; two of the six read complete profile tables (`page.tsx`, lines 21–69, 86–120). The code therefore has a floor of ten data calls for a nonempty default page, excluding authentication and cold authority internals. This is a code-path count, not a measured HTTP trace.
2. **Two filters defeat early pagination.** `evidence_approved` builds all approved word IDs from the global authority before its page RPC. `route_blocked` also sends approved pairs into `teaching_dictionary_admin_route_blocked_ids` and receives all blocked IDs before paging (`page.tsx`, lines 86–109; `supabase/migrations/20261025090000_teaching_dictionary_route_blocked_ids.sql`). Postgres paginates the final words, but the prerequisite authority and candidate set are global. These paths should remain consistent with the governed relationship evaluator.
3. **A single-word editor runs a broad lesson preflight after rendering.** `word-workspace.tsx`, lines 287–311, fetches `/api/admin/teaching-dictionary/[wordId]/lesson-readiness` with `no-store`; approval controls wait until it returns. That endpoint calls `loadLessonReadiness({ wordId, approvedSkillKeys })` (`route.ts`, lines 15–47). In `lesson-preflight.ts`, lines 222–268, the initial read loads all route content versions, release manifests, activation heads and profile data when only `wordId` is supplied; lines 281–329 load dependencies and authorities, and only later do lines 331–418 identify relevant route/skill pairs. This is a confirmed broad read path and a strong latency hypothesis, though its individual query cost has not been measured separately. The response includes preflight structures for the relevant routes; the API strips some package and other-word content before returning it.
4. **The editor has many round trips even before readiness.** `detail.tsx`, lines 46–175, starts twelve top-level reads for an existing word without a draft, plus `loadWordBaseFamilies`; it subsequently reads rollbacks, optional weak-vowel reviews/publications, and scoped relationship authority (lines 221–261). Some reads select `*`, and route history can load up to 100 content versions. The editor appears quickly in the measured case, so reducing this is secondary to the list and preflight, but it matters on cold and complex words.
5. **Save/Approve can multiply that wait.** `word-workspace.tsx`, lines 245–282, measures the save action, then re-fetches lesson checks after every save attempt and refreshes the whole route for a lesson save. `actions.ts`, lines 279–460, performs several dependent reads, draft/review/publication writes, and route staging/review. Skill approval uses a **global** relationship-authority read inside `applyTeachingDictionarySkillApprovals` (around lines 704–756) after word-scoped checks, then publishes each newly selected skill in a loop. These are code-confirmed cost opportunities; their elapsed times still need action instrumentation.
6. **Search SQL may scan the word table.** `teaching_dictionary_admin_filtered_page` uses `position(lower(p_search) in lower(w.normalised_word)) > 0` in `supabase/migrations/20261024210000_teaching_dictionary_admin_filtered_page.sql`. A contains search is useful, but ordinary B-tree indexes do not accelerate it. Use `EXPLAIN (ANALYZE, BUFFERS)` on realistic searches before choosing a trigram index; the 2,191-word table may be small enough that network and authority reads dominate.
7. **Family search is already bounded.** The manual picker waits for at least two characters, debounces 250 ms, and requests only matching families. Its API limits lexical and legacy results and returns at most 20 (`word-workspace.tsx`, lines 325–355; `app/api/admin/teaching-dictionary/family-search/route.ts`). Keep it scoped; add an index only if query plans and growth justify one.

## Implementation sequence

### 0. Establish component and action baselines

Add privacy-safe duration, Supabase request count, row count, and decoded JSON byte counters around the list RPC, relationship authority, route facts, editor initial read, readiness preflight, `performWorkspaceSave`, skill approval, family review, and route publication. Reuse `lib/adle/observability/read-metrics.ts` where possible; it already labels JSON bytes as a payload proxy, not billed egress. Capture at least 20 warm and 5 cold runs per page and each safe action on isolated staging, with Production read-only samples. Record first editor paint and checks-ready separately. Do not log words, learner content, secrets, or complete payloads. This phase decides where each subsequent change pays off.

### 1. Remove global authority from ordinary list reads

For `all`, `missing_metadata`, and ordinary search: get the 50 word IDs from the current SQL page RPC, then call the existing **word-scoped** relationship authority for those IDs. Keep the governed evaluator as the sole approval interpreter. Replace the two unfiltered profile reads with only IDs referenced by page members, or a small tagged profile lookup. Combine metadata, dictation, memberships, and route-content summary into a bounded SQL page result if the measured request overhead remains high. Preserve exact status and total-count behaviour. Expected files: `page.tsx`, `evidence-authority.ts`, relationship repository and optionally a new additive SQL function.

### 2. Make global filters database-backed without duplicating approval rules

Build an incremental approved-pair read projection produced by the existing relationship evaluator and refreshed on governed approval, withdrawal, resolver, family and route changes. Filter and paginate against it in SQL, including the blocked-member join. Avoid sending every approved pair to an RPC or returning every candidate ID to Next.js. Compare every projected pair/status to the current evaluator on staging, including withdrawal and historical cases, before switching reads. If this projection is not required after phase 1 measurements, defer it rather than adding a second authority. Expected files: the relationship writer/invalidation paths, `page.tsx`, additive projection migration and backfill/verification script.

### 3. Scope word readiness before loading route packages

First discover the word's approved pairs, published route content, and direct memberships. From those exact route/skill IDs, load only the corresponding profiles, activation heads, manifests, dependencies, and content versions. Continue validating whole lesson groups when group eligibility depends on other members, but reuse a group preflight keyed by immutable release/profile fingerprint rather than recomputing it for each word. Return only this word's blockers and the minimal group summary needed by the UI. Keep withdrawal and deactivation reads live or immediately invalidated. Expected files: `lesson-preflight.ts`, the readiness API, profile loaders and focused equivalence tests.

### 4. Shorten save feedback and scoped approvals

Replace the global authority read in `applyTeachingDictionarySkillApprovals` with its existing word-scoped equivalent. Measure and then batch independent reads and, where governance allows, candidate-package processing without changing editorial decisions. Keep the save result visible immediately; recheck affected route/skill pairs once, rather than performing a whole-page refresh plus a broad preflight. Preserve draft history and ensure a failed review does not masquerade as publication. Expected files: `actions.ts`, `word-workspace.tsx`, governed package helpers.

### 5. Verify behaviour and speed before release

On isolated staging, compare the old and new list rows, filter totals, word/skill approvals, blockers, withdrawal behaviour and route readiness for representative prefix, suffix, base-family, homophone, and unassigned words. Re-run the same timing protocol and report median and p95 only from adequate samples, with request and decoded-byte counts. Target a visible list and ready editor within a few seconds, but set the release threshold from the completed phase-0 baseline; the current three-run figures do not justify a savings percentage. Release one read path at a time, then repeat Production read-only timings and watch errors. Keep the existing source authorities and historical data intact.

## First implementation slice and staging proof

The prior staging [word-status handoff proof](admin-word-status-handoff-staging-2026-10-27.md) tested replacing the list's cached global authority with scoped reads. It reduced decoded bytes but added a query round and increased that read's measured time. The tiny profile tables were also slower to scope. Those proposed phase-1 changes were therefore **not** repeated here. The 60-second cached governed authority remains the list's approval source; phases 2 and 3 still need their own measured design.

Instead, `teaching_dictionary_admin_page_facts` returns facts for only the 50 displayed words in one service-role RPC. It replaces the eight metadata, dictation, membership, profile and route-content reads previously issued after pagination. Inactive metadata and unapproved dictation stay in the database but are omitted from this list response because neither can change its displayed status. The RPC does not interpret word–skill approval. The Teaching Dictionary skill approval action also now uses the existing governed **word-scoped** authority, rather than an uncached global read before processing one word.

The new RPC was installed on disposable staging only and compared with the previous eight-read projection across all nine pages of 424 active staging words, `careful` search and missing-metadata filter. The metadata, dictation, route-membership and route-content decisions matched in all 11 comparisons. A typical 50-word page moved from eight requests to one for this fact slice. In the final staged run, page 1 took 878/94 ms for old/new fact reads; page 2 took 220/111 ms. These are small, warm and noisy samples; neither establishes a Production page-time or billed-egress saving. Decoded body sizes also varied by page: page 1 was 33,759/30,234 bytes and page 5 was 24,620/29,949 bytes, so the change is a reliable request-count reduction but **not** a universal byte reduction. Staging function privileges were verified: service role can execute; anonymous and authenticated roles cannot.

Two staged word checks found that scoped and global governed approval decisions were identical. For one approved word the uncached authority read changed from 24 requests, 584,671 decoded bytes and 3,061 ms globally to 19 requests, 427,875 decoded bytes and 1,315 ms when scoped. For an unapproved word the corresponding measurements were 24/17 requests, 582,140/427,683 decoded bytes and 1,729/865 ms. These are action-helper measurements, not completed Save/Approve timings. A local browser against the staging database rendered the list, missing-metadata, search and evidence-approved views with HTTP 200 and 50/50/1/50 rows respectively; the first dev-server compile was excluded from any speed comparison.

The same staged readiness check still made 29 Supabase requests and decoded roughly 0.76–0.88 MB for one word. No readiness optimisation is claimed in this slice. Before changing the preflight, instrument its group discovery and validation separately and compare complete route decisions on staging. Do not narrow a group to one word when the route compiler needs all members.
